# RDNA4 + AITER + Triton + vLLM — Cross-Repo Audit

**Date:** 2026-05-20
**Trigger:** AITER upstream shipped first wave of consumer-RDNA4 (gfx1201) enablement ~2026-05-19. This audit consolidates the state of that enablement across AITER, Triton (upstream + ROCm fork), and vLLM, so we can decide what to vendor / cherry-pick / ignore.

> **Corrections appended 2026-05-20 evening, post-re-vendor investigation.** See "Corrections from verifying against actual repos" below the TL;DR — three claims from the original subagent reports need updating.

**Scope:** AMD R9700 (Navi 48, gfx1201, RDNA4, wave32, ~64 CUs). Not gfx1250 (which is MI450/CDNA, pre-silicon — see Terminology).

**Status of our integration at audit time:** `feat/aiter-turbo` branch, MAD-199 v2 chunks A+B shipped. AITER+turbo3/turbo4 correctness validated. Performance: AITER+f16 decode is ~30% slower than vanilla llama.cpp f16 at 64K ctx; AITER+f16 prefill is ~55% slower than vanilla. AITER+turbo3 64K decode is ~14% slower than AITER+f16. This audit was commissioned to find out why and what to do about it.

---

## TL;DR

1. **AITER's RDNA4 (gfx1201) support is ~5 days old.** PR #3236 (merged 2026-05-19) fixed a *silent buffer-resource fallback bug* where lowercase `__gfx11__`/`__gfx12__` tokens caused gfx12 to drop into an invalid `0xffffffff` buffer-rsrc path. **Our vendored kernel is from 2026-05-18 — one day before the fix.**

2. **We didn't vendor the host-side dispatcher.** `aiter/ops/triton/attention/unified_attention.py` has gfx1201 dispatch logic (`TILE_SIZE`, `BLOCK_M`, `waves_per_eu`, `num_warps`, `num_stages`, `target_num_prgms = cu_count * 4`) that we replaced with hardcoded CDNA-tuned constants in our wrapper.

3. **Triton's RDNA4 codegen has structural gaps**: pipeliner UAF on `num_stages>=2`, no block-pingpong scheduler, IN_THREAD_TRANSPOSE only in ≥3.7. Some are fixable (force `num_stages=1`, upgrade Triton); some are structural (no block-pingpong on WMMA archs).

4. **The single biggest unlanded perf op is Triton PR #7616** (`global_load_tr_b128` on gfx12) — single-instruction 8×8 transpose-load that skips LDS for non-K-contig dot operands. Exactly what attention K/V loads need. Stuck in draft since Jul 2025.

5. **vLLM does not yet use AITER on RDNA4** — gated to `on_mi3xx()`. Their stack pre-dates this week's AITER RDNA4 work. They officially direct RDNA4 users to Triton FA (`rocm.py` log line). This is **timing, not a verdict**.

6. **EmbeddedLLM/aiter** is the de-facto active RDNA4 staging fork. PRs #2351 (quant) and #2352 (rmsnorm) for gfx1201 have been open against upstream since March; PRs #3168/#3234 add ~5× speedup gemm_a8w8 configs for Mistral-3/Qwen3 shapes.

## Corrections from verifying against actual repos

When starting the re-vendor work (MAD-202), three claims from the original subagent audit did not survive a direct check against the upstream repo:

1. **The commit `be0ca6a` ("Tune 3D attention kernel on gfx1151") does not exist in `ROCm/aiter` upstream main.** The audit agent either hallucinated the SHA or read from an unmerged branch. The arch-aware tuning pattern it described as a "new precedent" actually *already exists* in the upstream host dispatcher `aiter/ops/triton/attention/unified_attention.py` (functions `select_2d_config` and `select_3d_config`) — it's the dispatcher we never vendored, not new code. The substantive recommendation (vendor the host dispatcher; let it pick arch-aware values) is unchanged; just the framing was wrong.

2. **PR #3236's buffer-resource fallback fix is in `opus.hpp` (C++), not in our vendored kernel `.py`.** Our integration doesn't include `opus.hpp` (we vendored only the Triton kernel file). So the "we likely carry the buffer-rsrc bug" claim probably does not apply to our integration at all. Worth a grep-confirm during MAD-202 work; but re-vendoring our `.py` alone wouldn't pick it up regardless.

3. **PR #3228's 28 new gfx1201 FP8 GEMM configs are JSON files only.** They live in `aiter/ops/triton/configs/gemm/` and only matter if AITER's `gemm_a8w8` path is exercised. We don't currently exercise it. Re-vendoring our `.py` alone does not pick them up; they belong with the MAD-206 cherry-pick story.

**Net effect on the re-vendor:** the actual kernel `.py` delta between our vendor SHA (`32e1e6d`, 2026-05-18) and upstream HEAD (`163e6a025`, 2026-05-20) is **a single 2-line accumulator-form refactor (PR #3231, commit `7f613da83`)**:
```diff
-        acc += tl.dot(P.to(V.dtype), V)
+        acc = tl.dot(P.to(V.dtype), V, acc=acc)
```
Applied at two sites (lines 353 and 672 — the V·scores accumulate in both 2D and 3D kernels). Marginal perf, no behavior change.

**The substantive re-vendoring work is the host dispatcher (MAD-203)**, which is now correctly scoped and was always going to be the load-bearing change. MAD-202 has been bundled into the same commit as MAD-203 since on its own it's a trivial 2-line patch.

## Section 1 — AITER (ROCm/aiter)

### 1.1 Host-side dispatcher we never vendored

Upstream `aiter/ops/triton/attention/unified_attention.py` (the dispatcher we don't have) contains gfx1201 logic:

```python
# Lines ~18-42:
TILE_SIZE         = 32 if arch.name == "gfx1201" else 16 if arch.is_rdna else 64
waves_per_eu      = 8  if arch.name == "gfx1151" else 6  if arch.is_rdna else 2
BLOCK_M           = 64 if arch.is_rdna else 128   # large-prefill 2D path
num_stages_2d     = 1
num_warps         = 4  if arch.is_rdna else 8

# Lines ~165-167 — 2D vs 3D dispatch:
cu_count          = get_num_sms()
target_num_prgms  = cu_count * 4          # 64*4=256 on R9700, 304*4=1216 on MI300
num_2d_prgms      = total_num_q_blocks * num_kv_heads
use_2d_kernel     = num_2d_prgms > target_num_prgms or max_seqlen_k <= 512 or sliding_window
```

Our wrapper `mt_aiter_unified_attn.h` instead hardcodes:

```c
#define MT_AITER_UATTN_NUM_SEGMENTS_PER_SEQ 32   // CDNA-tuned; on R9700 should follow cu_count*4 heuristic
#define MT_AITER_UATTN_BLOCK_Q              2    // matches
#define MT_AITER_UATTN_BLOCK_M              16   // upstream RDNA prefill uses 64
#define MT_AITER_UATTN_TILE_SIZE            32   // matches gfx1201 default
```

**Implications:**
- The `target_num_prgms = cu_count * 4` dispatcher routes work between the 2D (prefill-friendly) and 3D (split-K) kernels based on CU count. On 64-CU R9700 the threshold is 256; on 304-CU MI300 it's 1216. The 3D split-K path gets chosen far more aggressively on R9700, with each segment too small to amortize the `reduce_segments` epilogue. **Direct candidate cause of the prefill regression.**
- `MIN_SEGMENTS = 16 if TILE_SIZE ≤ 16 else 8` — with TILE_SIZE=32 the kernel forces ≥8 segments even on short contexts; pure overhead on R9700.
- `BLOCK_M=16` vs upstream's 64 for RDNA prefill is 4× less LDS reuse.

## Section 2 — Triton (triton-lang/triton + ROCm/triton)

### 2.1 Codegen status

- **WMMA v2 lowering for RDNA4 added in Triton 3.6.0** — handles f16/bf16→f32, plus several fp8 combos.
- **gfx1201 has NO arch-specific defaults** in `third_party/amd/backend/compiler.py` HIPOptions. All archs get `num_warps=4, num_stages=2, waves_per_eu=0, kpack=1, matrix_instr_nonkdim=0`.

### 2.2 Structural codegen gaps on RDNA4

| Gap | Impact | Fixable? |
|---|---|---|
| **`num_stages>=2` UAF on gfx1201** | Pipeliner crashes; tutorial pins `NUM_STAGES_OPTIONS=[1]` for HIP | Yes — force `num_stages=1` |
| **Block ping-pong scheduler is MFMA-only** | RDNA4 (WMMA) gets none of the mfma/memory overlap | No — structural, would need new pass |
| **WMMA shape constraints (issue #8931)** | Non-16-multiple blocks fall to worse layout | Yes — keep BLOCK_M/N/K multiples of 16 |
| **`matrix_instr_nonkdim`, `kpack` are MFMA-only** | No-op on WMMA archs | N/A — strip from RDNA path |
| **IN_THREAD_TRANSPOSE only in ≥3.7** | +5.7-23.6% on bf16 FA missed if on 3.6.0 | Yes — upgrade Triton |

## Section 3 — vLLM (vllm-project/vllm)

### 3.1 The headline

**vLLM does not use AITER on RDNA4 at all.** All AITER paths gated by `on_mi3xx()`:

```python
# vllm/_aiter_ops.py:66-86
def is_aiter_found_and_supported() -> bool:
    if current_platform.is_rocm() and IS_AITER_FOUND:
        from vllm.platforms.rocm import on_mi3xx
        return on_mi3xx()   # gfx942/gfx950 ONLY
    return False
```

`VLLM_ROCM_USE_AITER=1` is silently ignored on RDNA4. Backend priority on gfx1201:
`[ROCM_ATTN (HIP custom paged), TRITON_ATTN, TURBOQUANT]`.

`vllm/platforms/rocm.py` logger line is explicit: *"RDNA3/RDNA4 (gfx11xx/gfx12xx): Use Flash Attention Triton backend."*

**This reflects pre-2026-05-19 AITER state.** vLLM's gate was correct when written; it's a timing artifact, not a permanent design verdict. When AITER's gfx1201 path matures, vLLM is likely to expand the gate.

# Round 2 Research — 2026-05-20 late evening

After shipping MAD-202 + MAD-203 phase 1 (re-vendor + host dispatcher port) and MAD-203 phase 2 (NUM_SEGMENTS bump 32→128), we still had a 40-50% prefill gap between AITER+f16 and AITER+turbo3/4 at long context. A second wave of four parallel subagents was fanned out to find prior art on **non-uniform / Lloyd-Max KV quantization with native low-bit matmul hardware**. Sources: arXiv academic literature, GitHub implementations, AMD official ROCm docs/blogs, community practical reports (Reddit, HuggingFace, llama.cpp Discussions).

**Findings are convergent across all four sources.** This is the strongest possible signal.

## TL;DR for Round 2

1. **Nobody has published a Tensor-Core/WMMA-native attention kernel for Lloyd-Max non-uniform scalar codebooks.** It's a genuine unoccupied research niche.
2. **The pattern that DOES work — proven across 5 independent implementations — is in-register dequant pipelined directly into WMMA fragment writes**, skipping LDS round-trip entirely.
3. **Our 50% prefill gap is the LDS round-trip cost, NOT the fundamental dequant cost.** Much more tractable than feared.
4. **At least one community implementation specifically for our hardware (RDNA4 / gfx1201) claims turbo3 prefill BEATS f16 prefill at 32K — `jagsan-cyber/turboquant-rocm-llamacpp`.** If reproducible, that's our reference.
5. **AMD's official answer for KV is FP8** (Quark, ROCm vLLM docs). Turbo will remain a community/research path. FP8 KV (MAD-192) is the OEM-blessed production path.
6. **Correction: MXFP4 WMMA does NOT exist on RDNA4.** Earlier audit text said it did; that was wrong. MXFP4 matrix instruction lives only on MI350X (CDNA4). RDNA4's only sub-FP8 native option is INT4 (`v_wmma_f32_16x16x64_iu4`).

## Agent 1 — arXiv academic literature

### HIGH SIGNAL papers

**Quantix (PPoPP 2026, DOI 10.1145/3774934.3786423)** — directly tackles **3-bit non-uniform clustering quantization with 8 centroids per row** (same cardinality as turbo3) with fused dequant + matmul on Tensor Cores. Hardware-aligned bit shuffling + on-the-fly in-register dequant after loading centroids from SMEM into registers. **4.82× over FP16 cuBLAS.** Aimed at weights, but core trick (centroids in registers, dequant + MMA pipelined) maps directly onto turbo K.

**BitDecoding (HPCA 2025, arXiv:2503.18773)** — "Tensor Cores-Centric BitFusion Scheme" reshapes low-bit KV for direct INT4/INT8 Tensor Core consumption with **dequant fused into MMA pipeline**. 7.5× over FP16 FlashDecoding on RTX 4090, 8.9× on H100. Caveat: decoding-only, NVIDIA-only, uniform INT4 not Lloyd-Max.

**FLUTE (EMNLP Findings 2024, arXiv:2407.10960)** — Flexible LUT engine for non-uniform / non-power-of-2-bit weight quantization. Offline restructuring + LUT vectorization for Tensor Cores; 2-4× over GEMM for batch <32. Applied to NormalFloat (NF4) — structurally similar to Lloyd-Max scalar centroids. **Most directly transferable algorithm to turbo3/4.**

**CodeGEMM (arXiv:2512.17970, 2025)** — Codebook-centric GEMM eliminating per-element dequant via precomputed "Psumbook" (partial inner products between centroids and activations). Designed for VQ codebooks; with 8/16 centroids the Psumbook is tiny. Does not target Tensor Cores natively — gather-based on CUDA cores. Unclear utility on RDNA4 WMMA.

### Medium-signal KV cache work

- **KVQuant (NeurIPS 2024)** — per-channel + per-layer non-uniform sensitivity-weighted datatypes. Custom CUDA kernels, ~1.7× over FP16 matvec. Decode-only matvec, not prefill matmul, not Tensor-Core-based. Authors explicitly argue non-uniform dequant overhead is acceptable *because* decode is bandwidth-bound — exactly the trade-off that breaks down at our 64K prefill.
- **KIVI (ICML 2024)** — Asymmetric 2-bit (K per-channel, V per-token). Triton fused-dequant Q_MatMul kernel. Uniform affine, not codebook.
- **QServe (MLSys 2025)** — W4A8KV4 with two-level progressive group quant; everything lands on INT8 Tensor Cores. Uniform but register-level parallel decode pattern is reusable.
- **Atom, RotateKV, ZipCache, GEAR** — all uniform/affine + outlier handling. None tackle non-uniform codebooks at the Tensor Core level.
- **Marlin** — reference design for pipelining dequant with mma.sync. Uniform INT4 weights.
- **VQ-LLM (arXiv:2503.02236)** — code-gen for vector-quantized inference. H100/A100/4090. Weights not Lloyd-Max scalar KV.

### TurboQuant paper itself

Zandieh et al., arXiv:2504.19874 (ICLR 2026). The paper is **purely algorithmic** — random rotation + Beta-distribution Lloyd-Max scalar quant. No kernel description, no Tensor Core path, no fused-dequant kernel. Every implementation we've found is reinventing — which is why there's so much variance in reported numbers and approaches.

### Bottom line from arXiv agent

> "A turbo3/turbo4 RDNA4 prefill kernel that combines Quantix's in-register centroid dequant with BitDecoding's MMA pipelining looks like the unoccupied research niche. Two viable practical paths: (a) map 8/16 Lloyd-Max centroids to MXFP4's 16-value FP4 grid via best-fit reassignment so WMMA MXFP4 can be used directly (lossy but native); (b) ship a Quantix-style in-register dequant→bf16 WMMA path optimized for the 128-element block-norm layout."

(Path (a) doesn't apply to RDNA4 since MXFP4 WMMA isn't on this arch. Path (b) is what we should pursue.)

## Agent 2 — GitHub implementations

### HIGHEST SIGNAL finding

**`jagsan-cyber/turboquant-rocm-llamacpp`** — RDNA4 gfx1201 (RX 9070) turbo port. **Claims 2481 t/s turbo3 prefill vs 2349 t/s F16 prefill at 32K — turbo BEATING f16 on prefill, on our exact target arch.** No detail on whether WMMA is used in their kernel; must read the code. If real, this is our reference.

### Other turbo ports

- **`Indras-Mirror/llama.cpp-turboq-mtp`** — `fattn-mma-tbq4.cuh`, `tbq4-cuda.cuh`. Inline centroid LUT dequant inside FA inner loop, pre-rotated FWHT domain, CUDA Ada-only. 82+ tok/s @ 200K on 4090.
- **`TheTom/llama-cpp-turboquant`** — multi-arch (gfx1100/1201/942/950). Uses `ggml_cuda_dp4a` portable + **VEC FA forced for quantized KV** (scalar path, no WMMA).
- **`domvox/llama.cpp-turboquant-hip`** — gfx1100 port. Discussion #21526: *"WMMA was unnecessary on ROCm 6.3.1 and a regression on ROCm 7.2.1."* They explicitly avoid WMMA. **Despite that, hit turbo3 prefill within 1% of f16 on Qwen3.5-27B Q5_K_M (RDNA3, 7900 XTX).**

The split is informative: only jagsan-cyber claims to use WMMA effectively on gfx1201. The others either avoid WMMA (slow scalar path) or are NVIDIA-only.

### Production system patterns

- **vLLM, FA3, SGLang, TRT-LLM** — all pre-dequant K/V to f16/bf16 (or FP8) before matmul. No true "compute on quantized via tensor cores" path for non-uniform formats.
- **vLLM FP8 KV** — FA3 uses 2-level FP32 accumulation to fix long-context numerical drift. RDNA4/gfx1201 FP8 WMMA dispatch is patched but not upstream (vLLM #28649).
- **SGLang** — `--kv-cache-dtype fp8_e4m3` stores FP8 and dequants at read time to BF16/FP16 for attention. Backend-dependent.
- **FlashAttention-3** — FP8 forward uses WGMMA on FP8 tensor cores directly (1.2 PFLOPs/s, 2× FP16). Block quantization + incoherent processing (Hadamard) inside the kernel. Hopper-only.

### The proven pattern

- **Marlin** (IST-DASLab) — offline-reshuffled INT4 weights dequanted to FP16 *into tensor-core fragment layout in registers*, then MMA. Ampere-only, ~4× speedup vs FP16 GEMM. **W4A16 weight-side**, not KV.
- **SageAttention2** (thu-ml) — QK in **native INT4 tensor-core MMA** (per-thread quant), PV in FP8. INT32 accumulator → FP32 dequant → softmax. 3.9× vs FA2. SM80/89/90/120 only.
- **JohnTDI-cpu/rdna4-wmma-guide** — **fused MXFP4→FP16 WMMA via LDS-based LUT on R9700**, 40.8 TFLOPS (53% of FP16 peak), 3.8× vs separate dequant+hipBLAS for bs≤32. Documents the gfx12 lane mapping gotcha (`lane%16=column`, not row).

### Our own codebase

`ggml/src/ggml-cuda/fattn-vec.cuh` — quantized K is consumed via **scalar `vec_dot_KQ`** (dp4a/dot4 over 32-byte blocks, NOT WMMA). V is dequantized into f16 tile per timestep, fed to scalar accumulation. `fattn-mma-f16.cuh` (the MMA path) is f16/bf16 only, no quantized K support.

For our AITER path we DO use WMMA on dequanted f16 — but dequant to LDS first, then WMMA reads from LDS. We're missing the direct-to-fragment step. **That's the gap.**

### Bottom line from GitHub agent

> "The realistic path on gfx1201 is the SageAttention2 / Marlin pattern adapted to your scheme: dequant 8 centroids → FP16 fragment in registers via LDS LUT (Lloyd-Max table is tiny — 8 entries, fits in scalar GPRs or LDS), then `v_wmma_f32_16x16x16_f16`. This is what JohnTDI's MXFP4 kernel does, just with a non-uniform 8-entry LUT instead of E2M1 decode. You do not need INT4/MXFP4 WMMA — FP16 WMMA after register-resident LUT decode is the established fast pattern. None of the existing TurboQuant ports do this on AMD; they all use scalar `vec_dot`/dp4a."

## Agent 3 — AMD ROCm official guidance

### HIGH SIGNAL

**1. AMD's blessed answer for KV cache on RDNA4 is FP8 E4M3.**
- ROCm vLLM docs explicitly recommend FP8 KV (available since ROCm 6.2)
- AMD Quark (their own quant toolkit) supports FP8 W8A8 + FP8 KV cache + FP8 attention as a first-class path
- RDNA4 marketing: *"Radeon AI cards include dedicated AI accelerators optimized for new low-precision formats such as FP8 and BF8"*

**2. MXFP4 WMMA does NOT exist on RDNA4.**
- The instruction does not exist on gfx1201
- RDNA4 WMMA element types: fp16, bf16, fp8 (e4m3), int8, int4 (iu4)
- MXFP4 matrix instruction ships on **MI350X (CDNA4)** and is part of AMD's MI350-class roadmap, not RDNA4
- AMD GPUOpen "Using Matrix Cores of RDNA4" confirms the supported element set
- **The earlier audit text saying we could use MXFP4 WMMA on RDNA4 was wrong. Strike that option.**

**3. AMD's MXFP4 story is weights, not KV.**
- ROCm blogs frame MXFP4 as W4A16/W4A8 weight quantization on MI350, focused on large dense/MoE
- No AMD blog recommends MXFP4 for KV cache.

**4. Quark does NOT support Lloyd-Max / codebook KV quant.**
- Quark supports: int4/uint4 (groups 32/64/128), int8, fp8, mxfp4, mxfp6e2m3, mxfp6e3m2, bfp16, mx6
- Algorithms: AWQ, GPTQ, SmoothQuant, AutoSmoothQuant, Rotation
- **Non-uniform scalar codebooks are not in AMD's menu.** The whole turbo direction is community/research, not AMD-endorsed.

**5. AITER does not officially support gfx1201 yet.**
- gfx1201 missing from `_ARCH_TO_DEVICE` in `aiter/ops/triton/utils/arch_info.py`
- AITER's C++/ASM kernels are MI-only. Community fix: alias `gfx1201 → MI350X` (works because both use FP8 E4M3FN, not FNUZ)
- AITER v0.1.12 (Apr 2026) shipped no RDNA4-specific features

### Applicability

AMD's official answer for "KV cache on RDNA4" is **FP8 E4M3** with WMMA, not a 3.125-bit codebook. They have no hardware accelerator for codebook lookup KV; our dequant cost is by design — RDNA4 only has fast paths for formats whose element type appears in the WMMA ISA.

The **iu4 WMMA path is the only sub-FP8 native option** on gfx1201. If we want sub-FP8 KV with native matmul, switching to a uniform/symmetric INT4 codebook (or W4-style group quant) is the only format that gets RDNA4's matrix engine engaged natively.

### Future hardware hints

AMD's FP4-matrix roadmap is on **MI350X / CDNA4** (already shipping with mxfp4 WMMA). No public AMD guidance on gfx1300/gfx1400 (RDNA5) FP4 support — but the pattern "FP4 lands on CDNA first, then RDNA next gen" makes RDNA5 the plausible recipient of `v_wmma_*_mxfp4`. **For the lifetime of R9700, our hardware-native sub-FP8 options are stuck at INT4.**

## Agent 4 — Community practical reports

### HIGH SIGNAL findings

**1. Symmetric K/V is mandatory for fused FA on AMD HIP** (Discussion #22411, Krillian8, Apr 26 2026, 7900 XTX).
> "The fused FA kernels only support matching K/V quantization types."

Asymmetric `-ctk q4_0 -ctv f16` silently falls back to slow non-fused path. Code ref: `ggml-cuda/fattn*.cu`. **This is the single most likely cause of unexpected quantized-KV slowness on AMD — verify our turbo3 path uses symmetric K/V and hits a fused kernel.** Our AITER integration uses symmetric (turbo3 K + turbo3 V) so should be fine, but worth confirming.

**2. R9700 community KV consensus** (Discussion #21043, JohnTDI-cpu, Mar 26 2026).
> "for kv cache type: q4_0 is far better than q4_1, iq4_nl, q5_0, q5_1."

Recommends ROCm for >20B dense, Vulkan for MoE <20B active. Avoid `UD-Q4_K_XL` on ROCm; use pure Q4/Q8 to hit native INT4/INT8 hardware. Prefill: 960 t/s @ 3.6K → 755 t/s @ 47K on Qwen3.6-27B-Q8_0.

**3. turbo3 is essentially free on RDNA3** (Discussion #21526, domvox, Apr 6 2026).
- 7900 XTX (gfx1100), Qwen3.5-27B Q5_K_M
- turbo3 prefill 423 t/s (−1% vs f16)
- decode 29.49 t/s (−2%)
- GSM8K within noise

**Strongly implies our R9700 dequant slowness is implementation-specific to gfx1201, not fundamental to turbo3.**

**4. The "dequant > memory savings" failure mode is documented elsewhere** (Discussion #21829, simusid on H200).
- turbo3 was 15% slower than f16
- pauldev-hub: *"the overhead of dequantizing turbo3 back to fp16 during attention actually costs more than the memory savings gain"*
- Workaround offered: asymmetric `-ctk turbo4 -ctv q8_0` (but #22411 says this breaks fused FA on AMD)

**5. RX 9070 XT turbo3 crashes at large context** (Issue #21096, l33tm4st3r, Mar 28 2026, gfx1202 16GB).
- `HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION` with `-ctk turbo3 -ctv turbo3 -fa 1` at 200K ctx
- Workarounds: smaller ctx, q4_0 instead, or disable FA
- Suggests there are existing RDNA4 turbo correctness gaps worth knowing about

**6. Zolotukhin's R9700 essay (Apr 26 2026) — "Why FP16 KV cache is the wrong default for 128k context on 32GB RDNA4"** (https://zolotukhin.ai/blog/2026-04-26-why-fp16-kv-cache-is-the-wrong-default-for-128k-context-on-32gb-rdna4/)
> Pushes inline INT8/INT4 reads inside attention shader instead of offline scratch dequant to FP16 (~36ms/prompt overhead at 644 GB/s peak bandwidth).

**Directly validates the inline-quant attention recommendation.** External independent confirmation that the pattern works on our hardware.

### Supporting context

- **Vulkan beats ROCm on RDNA4 for decode in many cases**: 183 vs 150 t/s R9700 (Qwen3.5-35B-A3B); 62 vs 48 t/s 9070 XT (Qwen3.5-9B Q6_K_XL). Cause: Vulkan uses `KHR_cooperative_matrix` for RDNA4 matrix cores; vLLM/ROCm *"silently falls back to FP32 dequantization for all FP8 operations."*

- **CPU TurboQuant**: PR #21089 (elusznik) merged tbq3_0/tbq4_0 CPU types — indicates active mainline upstreaming of the turbo format.

## Synthesis: updated strategic picture

### Where our 50% prefill gap actually comes from

Our current AITER turbo kernel: turbo bytes → centroid lookup → multiply by norm → store to LDS → WMMA reads LDS.

The proven pattern (Marlin, Quantix, JohnTDI, SageAttention2): centroid LUT in registers → unpack turbo bytes per-lane → write directly to WMMA input fragment registers → WMMA executes.

**The cost we're paying is the LDS round-trip, not the fundamental dequant compute.** The Lloyd-Max LUT is tiny (8 entries for turbo3) and fits in scalar GPRs. We just haven't built the kernel that takes advantage of that.

### Realistic ceiling for turbo prefill on RDNA4

JohnTDI's RDNA4 MXFP4 kernel hits 53% of FP16 peak with the in-register-LUT pattern. domvox's gfx1100 turbo3 port hits parity with f16 (via scalar fattn-vec, not WMMA — they were probably bandwidth-bound).

jagsan-cyber's gfx1201 turbo port claims to BEAT f16 prefill. If reproducible, that's our target.

So the realistic ceiling for AITER+turbo3 prefill on R9700 isn't "10-15% below f16" as we feared — it's **at or above f16**.
