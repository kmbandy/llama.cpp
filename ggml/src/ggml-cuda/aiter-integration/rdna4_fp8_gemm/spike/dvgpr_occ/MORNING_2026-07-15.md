## THE RESIDUAL BUG (v3) — the thing to fix

**Symptom** (decentasn3_oracle_223146.log): oracle ok=4488 **bad=120** max_rel=**2.097** (triple-count),
occ[20]=12593 (production complete), STARVATION 84.6% (down from 99.8%), TF=0.4, occ[0]=0 (clean, no brick).

**The 4 SL_GEN gates closed the STAGE-walk / feed-pick paths** the reviewer found (SEV-1). So the
residual is elsewhere. **HYPOTHESIS (unproven — this is why we instrument, not guess):**
the **compute-side claim/STI straddle across a slot-reuse boundary**. A compute wave reads
DRAIN_HEAD=X, then does `s_alloc_vgpr` (grow, takes cycles) BEFORE `lds_fetch_add SL_RBNEXT`. During
the grow, DRAIN can advance past X and slot(X) gets recycled to X+POOL_N → the wave claims/reads STI
of the WRONG occupant. This race is LATENT in the base compute path (baseline single-coordinator is
oracle CLEAN) and only MANIFESTS under v3 because parallel production makes DRAIN advance fast enough
to hit the window. max_rel≈3× = a segment atomic-added into C three times.

**Committed next step: INSTRUMENT, do not theorize a 6th fix.** (Documented failure mode: I missed
this race class 4× by static reading; the review caught the 5th; the 6th must be measured.)

### Instrumentation plan (start here in the morning)
Add a DECENTASN-gated diagnostic counter that fires when a compute wave's post-grow state is
inconsistent with its pre-grow slot:
- Option A (cheapest): in `.Lflow_compute`, capture `SL_GEN[slot(DRAIN)]` BEFORE the grow; after the
  `lds_fetch_add SL_RBNEXT` claim, re-read `SL_GEN[slot]` and if it changed, `cnt_inc` a new DIAG
  counter (occ[NN]) and BAIL (shrink, no compute). If that counter is >0 and bad drops to 0, the
  hypothesis is confirmed AND fixed (re-verifying SL_GEN after the claim closes the straddle).
- Option B: gate the compute pick on `SL_GEN==DRAIN` re-checked after the claim, same as the feeder
  gates. This is the actual fix if Option A confirms.
- The reviewer's original tripwire (assert no STAGE/DRAIN advance where SL_GEN != head) is already
  structurally enforced by the 4 gates, so it won't fire — the residual is the compute CLAIM, which
  has no gate yet. Adding the post-claim SL_GEN re-check is the missing 5th gate.

**IMPORTANT nuance**: the compute path is HEAD-PINNED (MSSCAN=0). It reads DRAIN_HEAD. The base code
re-reads SL_STI AFTER the RBNEXT claim (DECODE_STI at ~line 2520, claim at ~2489) — so if we ALSO
re-verify SL_GEN==(the DRAIN index we claimed against) after the claim and bail on mismatch, that's
the surgical fix. Verify the exact register holding the DRAIN index survives to the re-check.
