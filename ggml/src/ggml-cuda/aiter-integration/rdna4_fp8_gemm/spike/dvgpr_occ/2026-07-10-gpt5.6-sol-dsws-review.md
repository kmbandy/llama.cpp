# Independent DSWS review - gpt5.6-sol - 2026-07-10

Repo inspected at `feat/wp-dflash-ds4`, `f61ec4f85231e9d40c5e4f0a452891b6a061641c`. I did not dispatch the GPU.

## Highest-severity findings

### 1. Run 8 cannot distinguish a completed non-final chunk from a hung kernel

The prepared Run 8 builds with `STAGINSTR=1` but does not set `TFPROBE=1`
(`/home/kmbandy/dsws_gpu_logs/fire_run8_groupsplit_frontier.sh:22-29`). `build_flow.sh` therefore passes
`TFPROBE=0` (`build_flow.sh:16-18`). At that setting `tfspan` emits no code, so no wave writes the exit tick
in `occ[3]` (`occ_kernel_dsws_flow.s:1117-1130`).

That matters because the host emits an EOP fence only for the final chunk (`occ_dispatch.cpp:1904-1905`).
For every earlier chunk, its only completion predicate is:

```
admitted && occW[0] == 0 && end != 0 && settled
```

where `end` is `occW[3]` (`occ_dispatch.cpp:1932-1938`). Run 8 uses `ML8_COOP_CHUNK=2` over 24 tiles, so
the first dispatch is non-final. It is therefore impossible for the host to declare that chunk done, even if
every wave has already executed `s_endpgm`. The external 12-second timeout fires before the host's internal
25-second timeout. The reported Run 6 state, `occ0=0` quickly with no fence, is exactly compatible with a
completed kernel followed by this host-side wait; it is not evidence of a group-split deadlock.

Offline confirmation: I assembled the documented `TFPROBE=0` `ACC_N=3` binary and disassembled it. There is
no `global_atomic_max_u32 ... offset:12` writer. Reassembling with `TFPROBE=1` emits that writer. This is a
direct emitted-ISA discriminator, not an inference from macros.

Recommendation: do not fire the current Run 8. Rebuild it with `TFPROBE=1`, or make the non-final completion
gate depend on a dedicated always-on kernel-exit counter instead of an optional performance probe. The first
corrected run should retain all current dispatch parameters and change only the build to:

```bash
WAVES=16 G=6 SEGK=32 ACC_N=3 POOL_N=1 STAGINSTR=1 TFPROBE=1 ./build_flow.sh
```

Confirmation is not merely a frontier line: the host must advance from chunk base 0 to base 2 before the
0.75-second guard. If it does, Runs 6-8 were host-observability failures. If it does not, only then is the
kernel liveness diagnosis live.

Confidence: **very high**.

### 2. The exit barrier is vulnerable to partial-workgroup residency, and `occ[80]` cannot observe it

Every flow wave decrements the global live count before entering the count-to-`WAVES` barrier
(`occ_kernel_dsws_flow.s:1919-1939`). A resident subset can therefore make `occ[0]` reach zero while waiting
for waves from the same 16-wave workgroup that have not yet been admitted. Smaller LDS changes workgroup
co-residency and scheduling, so this creates a plausible group-split-specific partial-residency convoy. The
`RETBAR_MAX` bound (`occ_kernel_dsws_flow.s:1937-1946`) makes it finite in instruction count, but one million
sleeping iterations per admitted batch can exceed the host/display safety window and look like a deadlock.

The advertised barrier telemetry does not discriminate this. `flow_snapshot` copies the LDS barrier count to
global `occ[80]` only from the coordinator's work loop (`occ_kernel_dsws_flow.s:1212-1247`, called at
`occ_kernel_dsws_flow.s:1517-1523`). Once drain completes, the coordinator writes all `ROLE_RETIRE` mailboxes
and immediately retires (`occ_kernel_dsws_flow.s:1601-1612`). Barrier arrivals occur after that, with no
remaining writer to refresh `occ[80]`. A streamed `barrier=0` or another stale value is therefore not a valid
exit-barrier verdict.

Offline confirmation: emitted ISA for `RETBARRIER=1` contains the compare against 16 and the one-million
iteration bound; a `RETBARRIER=0` build removes 148 bytes and the barrier compare while leaving one terminal
`s_endpgm`. This supplies a clean binary A/B discriminator.

Recommendation:

1. Add a one-shot global atomic arrival at `.Lflow_dead` (one operation per wave, not per spin) and stream that
   word directly. Also record an entry count or per-wave bitmask immediately after the initial lean allocation.
   `arrivals < entries < WAVES` identifies partial launch; `arrivals < entries == WAVES` identifies a stuck
   entered wave.
2. Run the corrected `TFPROBE=1` diagnostic once with `RETBARRIER=1`, then once with `RETBARRIER=0`. If only
   the latter advances to chunk 2, the barrier is causal. If both advance, the old Run 8 was entirely the host
   completion-gate bug.
3. Do not use an all-waves software barrier as a permanent EOP workaround unless full-workgroup admission is
   an established hardware contract for this launch. A per-workgroup single terminal writer after a monotone
   work-completion count is safer than holding resident waves for not-yet-resident peers.

Confidence: **high** on the telemetry defect; **medium-high** on partial residency as the residual kernel-side
mechanism.

### 3. Flow binaries are not configuration-identifiable at dispatch

The host sizes LDS from runtime `FLOW_POOL_N`, `DSWS2_ACC_N`, `DSWS2_SEGK`, `G`, `FM`, and `FN`
(`occ_dispatch.cpp:1803-1815`), but selects a flow binary using only `Wlaunch`
(`occ_dispatch.cpp:6184-6187`). The same `occ_dsws2_w16_flow_gd.bin` name can therefore mean `ACC_N=6`, 3,
or 2, and can also hide a different pool depth or segment size. A stale safe bin plus new runtime geometry can
silently under-allocate LDS or use incompatible address immediates.

Offline confirmation: under otherwise identical documented flags I measured distinct hashes and sizes:

| ACC_N | `.text` bytes | SHA-256 prefix |
|---:|---:|---|
| 6 | 16196 | `f1737a27f79d` |
| 3 | 11624 | `582de588c6e3` |
| 2 | 10072 | `e121398576bc` |

All three would be loaded through the same host filename at `Wlaunch=16`.

Recommendation: encode at least `w/g/segk/pool/acc` in the filename and refuse a missing exact match. Stronger:
emit a small configuration signature to fixed `occ[]` words at entry and have the host compare it before it
trusts any diagnostic or oracle result.

Confidence: **very high**.

### 4. The advertised bank-free `WOFLUSH` occupancy alternative is currently unbuildable

The source advertises `WOFLUSH=1, ACC_N=0` as the roughly 8 KB LDS route to several workgroups per CU
(`occ_kernel_dsws_flow.s:90-98`). Group-split arithmetic is unconditional, however: it evaluates `G % ACC_N`
and `G / ACC_N` (`occ_kernel_dsws_flow.s:310-315`).

Offline confirmation: assembling the advertised `WOFLUSH=1 ACC_N=0` configuration fails at line 310 with
`expected absolute expression`, followed by undefined `GROUPS` conditionals. Using a positive `ACC_N` does
not recover the intended design: the direct-C path offsets by local `s33` only
(`occ_kernel_dsws_flow.s:1725-1731`), so a group-split WOFLUSH build aliases later groups onto the first local
row range.

Recommendation: separate `WORK_RB_N` from `ACC_N`. In WOFLUSH mode, set `WORK_RB_N=G`, `GROUPS=1`, allocate
zero banks, and address C with the actual rowblock. Add an assembly-only matrix containing the advertised
`ACC_N=0` cell before treating this as an occupancy fallback.

Confidence: **very high**.

## Group-split assessment and a better LDS lever

Within the current supported domain (`sti < 2^28`, `WOFLUSH=0`), the group-to-row and C-store arithmetic is
correct. Compute maps `actual_rowblk = group*ACC_N + local` for A (`occ_kernel_dsws_flow.s:1686-1695`), and
the completer adds `group*(ACC_N*FM*FN*1024)` before storing `ACC_N` banks
(`occ_kernel_dsws_flow.s:1793-1819`). My exhaustive small integer check covers rows 0 through 5 exactly once
for both `ACC_N=3` and `ACC_N=2`; the C group strides are 24576 and 16384 bytes respectively.

The packing is not collision-free for all host-accepted shapes. The coordinator ORs unmasked `sti` with the
group nibble (`occ_kernel_dsws_flow.s:1561-1567`), while the host only checks that pool counts fit 32 bits
(`occ_dispatch.cpp:6152-6155`). `(group=0, sti=2^28)` and `(group=1, sti=0)` both pack as `0x10000000`.
Add a host refusal requiring `TOTAL_super < 2^28` for group-split, plus a matching documented kernel contract.
Offline confirmation is the direct packing calculation above; a boundary CPU enumerator should become part of
the offline build gate.

There is also a lower-risk way to get 2 WG/CU while retaining B reuse: make resident A group-local too. Today
each group stages and stores all `G` A rowblocks: `ARES_BYTES` is proportional to `G`
(`occ_kernel_dsws_flow.s:275-280`), and `ASTAGE_R` claims `G`, uses a `G` stride, and publishes done at `G`
(`occ_kernel_dsws_flow.s:751-790`). Yet compute consumes only the current group's `ACC_N` rows. For
`SEGK=32, ACC_N=3`, group-local A changes LDS from:

```
256 + B(2048) + A_all_G(6144) + banks(24576) = 33024
```

to:

```
256 + B(2048) + A_group(3072) + banks(24576) = 29952
```

Two such workgroups fit under 64 KB, using two groups instead of the `ACC_N=2` variant's three B rescans. The
implementation must preserve the group long enough for A staging, load global A row
`group*ACC_N + local`, store it at local A index, and change `ARDONE`'s target to `ACC_N`.

Offline discriminator: assemble/RGA the compact-A `ACC_N=3` cell, confirm LDS 29952 and zero spills, disassemble
all A LDS offsets to prove they remain inside the compact slot, and run a CPU address enumerator that proves
all six global rowblocks map once to local indices 0..2 across two groups. Only after those pass should one
GPU oracle run compare compact-A against the current `ACC_N=3` arithmetic.

Confidence: **high**.

## Flow protocol and coast review

The architectural choice I would keep is the separation between monotone work frontiers and a lazy role
economy. The coordinator is the only assign/reset writer, and compute-to-feed coast does useful work instead
of polling a generation. This is simpler than the Phase-B distributed conversion handshake and makes failures
more localizable.

The coast is safe as emitted for the reviewed `ACC_N=3` cell. Before the first grow, the largest referenced
VGPR is `v14`. The grow instruction is `s_alloc_vgpr 0x70`; WMMA then uses `v32..v107`. The grow-fail/coast
path uses staging registers only through `v19`, below the lean allocation of 32. LDS helpers preserve and
restore `exec`, and the emitted lane-zero masks close before returning to the unified loop. I found no OOR
read or exec-mask leak on this path. Confidence: **high**.

The three-frontier publication proof is weaker than the design claims under the stated no-release/acquire LDS
model. Assignment resets six counters, writes STAMP, and finally plain-stores `ASSIGN_HEAD`
(`occ_kernel_dsws_flow.s:1574-1595`). Each helper drains the writer's own LDS operation
(`occ_kernel_dsws_flow.s:442-453`, `576-588`), but there is no reader-side validation that the observed STAMP
belongs to the observed head. Single-writer discipline prevents competing resets; it does not by itself turn
two separate LDS locations into an atomic publication.

I would keep monotone heads but make slot content self-validating: store the full monotone local head/generation
in STAMP, and have feed/compute return empty unless `STAMP.generation == head` both before and after claiming.
An even stronger variant uses never-reset per-slot work/done counters whose expected values are derived from
the monotone generation. Both retain the non-blocking hot loop. Offline discriminator: extend the CPU model
with adversarial stale reads of every plain LDS field (not just C++ relaxed atomics) and require that a stale
read can cause only an empty/retry result, never a claim against the wrong generation.

Confidence: **medium**; this is a proof gap, not a reproduced failure.

## Phase-B newer work

For Phase-B, each non-claimer has exactly one terminal over-claim and one quiesce bump per observed epoch in
the emitted role control flow: each role follows one epoch, drains its role counter, reaches its single
`*_quiesce` block, bumps, then redispatches to a next-epoch follow loop (`occ_kernel_dsws.s:1416-1489`,
`1495-1569`, `1577-1818`). A conversion changes the next role only after the current role's over-claim. I did
not find a normal skip or double-count path. A wave stuck in initial allocation/init/follow or in a feed-to-
compute grow can skip the bump permanently; that is the liveness class the straggler model already exposes.
The flow kernel has no analogous "one bail per super-tile" property: its workers may do zero or multiple units
for a slot, and only check in once at final retirement.

The SENSOR FIX needs versioning. The claimer writes the unversioned `OCCA_PUB_OFF/OCCB_PUB_OFF` pair before
the combined advance gate closes, and intentionally omits `s_wait_dscnt` (`occ_kernel_dsws.s:1312-1328`).
Followers read that pair during the current epoch's post-work decision (`occ_kernel_dsws.s:1462-1469`,
`1542-1549`, `1782-1796`). Early followers can therefore decide from the previous super-tile while later
followers decide from the current partial/final peak. The pair can also be observed from different publishes.
That does not corrupt GEMM data, but it defeats the claim that all decisions consume one defined delayed
sensor sample and can create opposing conversions in the same epoch.

Recommendation: double-buffer the sensor by epoch parity, publish both values after the full completion and
quiesce gate, drain the stores, then advance. Followers should read only the previous parity. Offline
discriminator: a scheduler model that delays each follower around publish must show every follower in an
epoch consuming the same `(occA,occB,generation)` tuple. Disassembly should show the two stores and wait before
the epoch/frontier advance.

Confidence: **medium-high**.

  `ec2e3594...`. `DIAG=1` changes no bytes when `CONV=0`. This supports the gated-baseline claim; it does not
  mean CONV=0 and CONV=1 are identical to each other.
- CPU models: reproduced control-model `ALL PASS`, quiesce 0/400 stalls under both orderings, envelope 0/200
  stalls at peak concurrency 1/2/3, and the stated straggler results. These models support Phase-B protocol
  bookkeeping, but they do not model the flow exit barrier, Run 8 host completion, or versionless sensor
  publication.
- The "about 7x under bind" statement is an estimate, not a re-measured threshold. `263/128 = 2.05` fat
  waves/SIMD is valid as a device-wide average at the global peak. The 13-14 comparison comes from the
  calibratable `VBUDGET=1536` (`occ_kernel_dsws_flow.s:920-936`) and assumes a useful distribution across
  SIMDs. The source itself labels that budget "Calibrate." I accept the measured 263, but not the 7x factor as
  established until a per-SIMD distribution or grow-fail sweep calibrates the actual boundary.
