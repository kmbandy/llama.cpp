NETWORK INVESTIGATION (kmbandy: "never seen it use more than 300Mbps on a
hardwired gigabit pair"). VERDICT: THE NETWORK IS INNOCENT — THE WIRE HAS
THE SAME DISEASE AS THE DRIVE: DUTY CYCLE.

Measured (python socket probes, boxes idle, delivery-confirmed):
  path        bulk     10MB bursts  1MB bursts  full-duplex aggregate
  LAN direct  941.6    896          872         1766
  tailscale   892.2    844          695         1570   (all Mbps)
  - Tailscale is DIRECT (192.168.1.33:41641, no DERP relay); both NICs
    negotiate 1000/full; tailscale0 MTU 1280.
  - The tunnel costs ~5% bulk, ~20% on 1MB bursts (packet tax + ramp) —
    real but minor; nothing caps at 300.

THE 300 Mbps IS THE APPLICATION'S SHAPE: per layer, one 10-40 MB burst
(~100-400 ms of wire time at ~850 Mbps) followed by the rest of the
~1.3 s layer cycle (worker reads + compute + spine work) with the wire
IDLE. Duty cycle ~25-35% -> ~300 Mbps average. Identical structure to
the 07-31 NVMe finding ("the drive is idle 60-70%; the storage problem
is duty cycle, not queue depth"). The serial layer loop starves both.

IMPLICATIONS:
  1. ~3x wire headroom exists during the idle windows — a point IN FAVOR
     of the §4 predictor: its prefetch/hint bytes ride wire time that
     nothing else uses.
  2. cheap sysctl worth applying anyway (kmbandy sudo, both boxes,
     persist in /etc/sysctl.d/): net.ipv4.tcp_slow_start_after_idle=0 —
     with =1 (current), every post-idle burst re-climbs cwnd from ~15 KB,
     taxing exactly this traffic shape; standard practice for bursty RPC
     on controlled LANs. Optionally raise net.core.wmem_max (4 MB now)
     toward 32 MB so a whole ACTS-scale frame fits in kernel buffers.
  3. The in-run retransmits/stalls (~800-1000 segs/arm, RTO chains) did
     NOT reproduce from idle boxes — they are load-window-specific
     (tailscaled CPU contention during compute + fq_codel drop batches
     on burst overshoot). Next diagnosis rides a REAL run: pidstat-delta
     on tailscaled + nstat during a prefill-heavy arm. If confirmed,
     moving the dispatch data path to LAN IPs (IPMAIN/IP2026, 3f5a7c7b1)
     removes tailscaled from the data plane entirely — encryption is

CAPTURE FORMATS

WP_DRAFT_CAPTURE=<path> is an append-only binary stream. Its one-time header is
four little-endian u32 values: magic WPD1 (0x31445057), version 1, n_embd, and
dtype (1 = f32). Each block record is marker WDR1 (0x31445257), u64 block_id,
u32 n_drafted, n_drafted llama_token/i32 token ids, then
n_drafted*n_embd f32 NextN embedding values. Records are flushed individually.

WP_PREDICT_CAPTURE=<prefix> writes <prefix>.<pid>.bin. Existing routing records
are unchanged: WPC1 magic, then i32 layer, n_tokens, n_embd, n_expert_used,
n_tokens*n_embd f32 activations, and n_tokens*n_expert_used i32 selected experts.
The added raw-token record is marker WBT1 (0x31425457), u32 n_tokens, followed
by n_tokens i32 token ids (including mask tokens). It is flushed per record and
can be interleaved with the existing WPC1 records in stream order.
